DATABASE CREATION ENGINE
DESIGN CONTRACT
===============================================================


1. PURPOSE
===============================================================

The Database Creation Engine is responsible only for creating,
verifying, and maintaining the creation state of the physical database
artifacts for one dedicated Backend Code Synchronization.

The Database Creation Engine and the Database Removal Engine are two
separate engines with separate responsibilities.

This document defines only the Database Creation Engine.

The Database Creation Engine must be safe to execute repeatedly for the
same synchronization.

A repeated creation request must never create duplicate ownership
artifacts for the same dedicated Submenu Code.


2. CORE OWNERSHIP PRINCIPLE
===============================================================

Every submenu-level Backend Code Synchronization that requires a
database table is identified by its dedicated Submenu Code.

The Submenu Code is the permanent ownership key for all database
artifacts created for that synchronization.

Example:

SUB-003-001-001

        ↓

Company Entity

        ↓

Company Table

        ↓

Dedicated Migration

        ↓

Dedicated Designer File

        ↓

Dedicated Snapshot Section

The Code Synchronization ID is used to locate and load the requested
synchronization.

The Code Synchronization ID is NOT the permanent ownership identity of
the database artifacts.

The Submenu Code is the permanent database artifact ownership identity.


3. LOCKED OWNERSHIP RULE
===============================================================

One dedicated Submenu Code represents exactly one database
synchronization unit.

Therefore, one Submenu Code must not create:

- Multiple dedicated migration pairs.
- Multiple dedicated designer files.
- Multiple ownership snapshot sections.
- Multiple database creation units for the same generated entity/table.

Example:

SUB-003-001-001

Normalized:

SUB003001001

Valid ownership artifacts:

{Timestamp}_AutoSync_SUB003001001.cs

{Timestamp}_AutoSync_SUB003001001.Designer.cs

AUTO SYNC SNAPSHOT START : SUB-003-001-001

AUTO SYNC SNAPSHOT END : SUB-003-001-001

The timestamp may be different between different submenu ownership
units, but the same Submenu Code must always resolve to the same
dedicated migration ownership unit.

A second creation attempt for the same Submenu Code must reuse and
verify the existing ownership artifacts.

It must not create another migration with a new timestamp.


4. DATABASE CREATION IDENTITY
===============================================================

The Database Creation Engine receives:

Code Synchronization ID

        ↓

Load Code Synchronization

        ↓

Load dedicated Submenu

        ↓

Read dedicated Submenu Code

Example:

SUB-003-001-001

        ↓

Normalize Migration Key

SUB003001001

        ↓

Use Submenu Code as permanent ownership key

        ↓

Locate existing artifacts by that ownership key

The normalized migration key is derived only from the Submenu Code.

Example:

Original Submenu Code:

SUB-003-001-001

Normalized Migration Key:

SUB003001001

Migration Name:

AutoSync_SUB003001001


5. DEDICATED ARTIFACT NAMING RULE
===============================================================

The dedicated migration name must be:

AutoSync_{NormalizedSubmenuCode}

Example:

AutoSync_SUB003001001

The physical files generated by Entity Framework will follow:

{Timestamp}_AutoSync_{NormalizedSubmenuCode}.cs

{Timestamp}_AutoSync_{NormalizedSubmenuCode}.Designer.cs

Example:

20260822230000_AutoSync_SUB003001001.cs

20260822230000_AutoSync_SUB003001001.Designer.cs

The Code Synchronization ID must not be appended to the migration name
as a permanent ownership suffix.

The Submenu Code alone determines the dedicated migration ownership.


6. REQUIRED IDEMPOTENT CREATION BEHAVIOR
===============================================================

The Database Creation Engine must be idempotent.

This means that executing the creation operation multiple times for the
same dedicated Submenu Code must not duplicate database artifacts.

The required behavior is:

FIRST ATTEMPT

Submenu Code has no dedicated migration.

        ↓

Identify generated Entity / Table.

        ↓

Create one dedicated migration pair.

        ↓

Apply migration.

        ↓

Verify database table.

        ↓

Verify snapshot ownership section.

        ↓

Return success.


SECOND OR LATER ATTEMPT

Submenu Code already has a dedicated migration pair.

        ↓

Do not create a new migration.

        ↓

Locate the existing dedicated migration.

        ↓

Verify migration pair integrity.

        ↓

Verify migration application state.

        ↓

Apply the existing migration if it is not yet applied.

        ↓

Verify the dedicated database table.

        ↓

Verify the dedicated snapshot ownership section.

        ↓

Return success.


EXAMPLE OF PROHIBITED BEHAVIOR

First attempt:

20260822230000_AutoSync_SUB003001001.cs

Second attempt:

20260823070948_AutoSync_SUB003001001.cs

This is prohibited.

Both files represent the same Submenu Code and therefore duplicate the
same database synchronization ownership unit.


7. EXISTING ARTIFACT DETECTION
===============================================================

Before any new migration is created, the Database Creation Engine must
search for existing artifacts using the normalized Submenu Code.

Required migration file search pattern:

*_AutoSync_{NormalizedSubmenuCode}.cs

The search must exclude:

*.Designer.cs

Required designer file search pattern:

*_AutoSync_{NormalizedSubmenuCode}.Designer.cs

The engine must evaluate the ownership artifacts before generating a new
migration.


8. EXISTING ARTIFACT STATES
===============================================================

STATE A
No migration file and no designer file exist.

Result:

A new dedicated migration pair may be created.


STATE B
Exactly one migration file and exactly one matching designer file exist.

Result:

The existing migration ownership unit must be reused.

No new migration may be created.


STATE C
Migration file exists but matching designer file is missing.

Result:

Creation must fail with an artifact integrity error.

The engine must not create a second migration.


STATE D
Designer file exists but matching migration file is missing.

Result:

Creation must fail with an artifact integrity error.

The engine must not create a second migration.


STATE E
More than one migration ownership pair exists for the same normalized
Submenu Code.

Result:

Creation must fail with a duplicate ownership artifact error.

The engine must not guess which migration is correct.

The engine must not create another migration.


STATE F
Migration pair exists but the migration is not applied to the database.

Result:

Reuse the existing migration ownership unit and execute database update.

Do not create a new migration.


STATE G
Migration pair exists and the migration is already applied.

Result:

Do not create a new migration.

Verify the dedicated database table and snapshot ownership section.

Return success if all required artifacts are valid.

10. PENDING MODEL CHANGES RULE
===============================================================

The result of an Entity Framework pending model changes check must not
be used as the ownership decision for whether a dedicated migration
should be created.

The ownership decision must first be based on the dedicated Submenu
Code and its existing artifacts.

Therefore:

Existing migration for the Submenu Code
+
Pending model changes detected

does NOT automatically mean:

Create another migration for the same Submenu Code.

The engine must first determine whether those pending model changes
belong to:

- The same dedicated synchronization.
- Another synchronization.
- A manually changed model.
- An incomplete or invalid generated state.

The Database Creation Engine must not create a duplicate migration merely
because Entity Framework reports pending model changes.

Artifact ownership detection always comes before new migration creation.


11. PHYSICAL RESPONSIBILITIES
===============================================================

The Database Creation Engine is responsible for creating and verifying
the following physical database artifacts for one dedicated Submenu Code.


1. DEDICATED MIGRATION FILE

Example:

20260822230000_AutoSync_SUB003001001.cs

There must be only one active dedicated migration ownership file for one
Submenu Code.


2. DEDICATED MIGRATION DESIGNER FILE

Example:

20260822230000_AutoSync_SUB003001001.Designer.cs

The designer file must belong to the same dedicated migration ownership
unit.


3. DATABASE TABLE

The dedicated migration is applied so that the generated table for the
identified submenu/entity is physically created in the database.

If the table already exists because the dedicated migration was already
applied, the engine must verify it instead of attempting to recreate the
ownership artifacts.


4. DEDICATED SNAPSHOT REGISTRATION

A dedicated marked ownership section is maintained inside:

AppDbContextModelSnapshot.cs

Each Submenu Code must have its own dedicated marked section.


12. SNAPSHOT MARKER RULE
===============================================================

Each database synchronization must have one dedicated snapshot ownership
block.

Format:

//===========================================================

// AUTO SYNC SNAPSHOT START : {SubmenuCode}

//===========================================================

{Entity snapshot configuration}

//===========================================================

// AUTO SYNC SNAPSHOT END : {SubmenuCode}

//===========================================================

Example:

//===========================================================

// AUTO SYNC SNAPSHOT START : SUB-003-001-001

//===========================================================

// Company entity snapshot configuration

//===========================================================

// AUTO SYNC SNAPSHOT END : SUB-003-001-001

//===========================================================


13. SNAPSHOT IDEMPOTENCY RULE
===============================================================

Before inserting a dedicated snapshot section, the Database Creation
Engine must search for:

AUTO SYNC SNAPSHOT START : {SubmenuCode}

and:

AUTO SYNC SNAPSHOT END : {SubmenuCode}

Required behavior:

- If neither marker exists, create the dedicated section.
- If both markers exist as one valid block, reuse and verify the block.
- If only one marker exists, fail with a snapshot integrity error.
- If multiple blocks exist for the same Submenu Code, fail with a
  duplicate snapshot ownership error.
- Never insert another snapshot section for the same Submenu Code.


14. ARTIFACT OWNERSHIP
===============================================================

All generated database artifacts must remain traceable to the exact
Submenu Code.

Example ownership:

Submenu Code:

SUB-003-001-001


Migration:

20260822230000_AutoSync_SUB003001001.cs


Designer:

20260822230000_AutoSync_SUB003001001.Designer.cs


Snapshot:

AUTO SYNC SNAPSHOT START : SUB-003-001-001

AUTO SYNC SNAPSHOT END : SUB-003-001-001


Database Table:

The dedicated generated table identified from the corresponding Backend
Code Synchronization.


15. SUCCESS RESULT RULE
===============================================================

The result must clearly distinguish between:

A. Newly created.

Example meaning:

The dedicated migration did not previously exist. The engine created the
migration pair, applied it, and verified the database artifacts.


B. Existing migration applied.

Example meaning:

The dedicated migration pair already existed but had not yet been
applied. The engine reused the existing migration and completed database
creation.


C. Already created and verified.

Example meaning:

The dedicated migration was already present and applied. The engine did
not create a new migration. It verified the migration ownership,
database table, and snapshot ownership section.


The result must never falsely report that a new migration was created
when the same Submenu Code already owns an existing migration.


16. DATABASE CREATION ENGINE BOUNDARIES
===============================================================

The Database Creation Engine SHALL:

- Receive the Code Synchronization ID.
- Load the corresponding Code Synchronization.
- Validate that the synchronization is Backend.
- Load the dedicated Submenu.
- Read and validate the dedicated Submenu Code.
- Normalize the Submenu Code into the migration key.
- Identify the generated Entity and Table.
- Search for existing migration ownership artifacts before creating
  anything.
- Reuse an existing valid migration pair for the same Submenu Code.
- Create one dedicated migration file only when no valid ownership
  migration exists.
- Create one dedicated designer file belonging to that migration.
- Apply the dedicated migration when required.
- Verify that the dedicated database table exists.
- Insert one dedicated marked snapshot ownership section when required.
- Verify an existing valid snapshot section on repeated execution.
- Detect incomplete or duplicate ownership artifacts.
- Fail safely instead of creating additional duplicate artifacts.
- Return the final creation or verification result.


17. DATABASE CREATION ENGINE SHALL NOT
===============================================================

The Database Creation Engine SHALL NOT:

- Remove database tables.
- Delete migration files.
- Delete designer files.
- Remove snapshot sections.
- Perform database rollback.
- Perform database removal operations.
- Create a second migration for the same Submenu Code.
- Create a second designer file for the same migration ownership unit.
- Create a second snapshot section for the same Submenu Code.
- Use the Code Synchronization ID as the permanent database artifact
  ownership key.
- Treat every creation request as a new migration request.
- Create a new migration solely because pending model changes are
  detected.
- Guess which artifact is correct when duplicate ownership artifacts
  already exist.


18. FAILURE SAFETY RULE
===============================================================

When the engine detects any ambiguous, incomplete, or duplicate
ownership state, it must stop and return a clear failure result.

Examples:

- Multiple migration files match the same Submenu Code.
- Multiple designer files match the same Submenu Code.
- Migration file exists without matching designer file.
- Designer file exists without matching migration file.
- Multiple snapshot sections exist for the same Submenu Code.
- Snapshot start marker exists without matching end marker.
- Snapshot end marker exists without matching start marker.
- Existing migration ownership cannot be matched to the expected
  generated entity/table.

The engine must never solve these states by silently creating another
migration.


19. DATABASE REMOVAL COMPATIBILITY
===============================================================

The Database Creation Engine must create and preserve every artifact in
a way that allows the future Database Removal Engine to identify the
exact ownership unit by the dedicated Submenu Code.

The Database Removal Engine will use the same Submenu Code to identify:

- The exact migration file.
- The exact designer file.
- The exact snapshot section.
- The exact database table.

Example:

SUB-003-001-001

        ↓

*_AutoSync_SUB003001001.cs

        ↓

*_AutoSync_SUB003001001.Designer.cs

        ↓

AUTO SYNC SNAPSHOT START : SUB-003-001-001

        ↓

AUTO SYNC SNAPSHOT END : SUB-003-001-001

        ↓

Dedicated database table


20. DATABASE REMOVAL SEPARATION
===============================================================

The Database Creation Engine creates and verifies artifacts.

The Database Removal Engine will later be responsible for identifying
and removing the exact artifacts owned by the same dedicated Submenu
Code.

Creation logic must therefore preserve ownership consistency.

Creation must not perform removal operations.

Removal logic must not be introduced into the Database Creation Engine.


21. LOCKED DESIGN PRINCIPLE
===============================================================

One dedicated Submenu Code represents the permanent ownership identity
of one database synchronization unit.

That Submenu Code connects:

Code Synchronization Request

        ↓

Dedicated Submenu Code

        ↓

Generated Entity

        ↓

Dedicated Database Table

        ↓

One Dedicated Migration File

        ↓

One Dedicated Designer File

        ↓

One Dedicated Snapshot Section


The Code Synchronization ID starts the request.

The Submenu Code owns the database artifacts.

The Database Creation Engine must therefore be idempotent by Submenu
Code.

Repeated execution for the same Submenu Code must:

- Find the existing ownership artifacts.
- Reuse the valid dedicated migration.
- Apply it only if necessary.
- Verify the database table.
- Verify the snapshot section.
- Return the correct result.

Repeated execution must never create another timestamped migration for
the same Submenu Code.


22. FINAL LOCKED RULE
===============================================================

Before creating any new database migration, the Database Creation Engine
must always answer this question:

"Does this dedicated Submenu Code already own a migration, designer,
snapshot section, or completed database creation unit?"

If the answer is YES:

Do not create another migration.

Locate, reuse, apply if necessary, and verify the existing dedicated
artifacts.

If the answer is NO:

Create exactly one dedicated ownership unit for that Submenu Code.

This rule is mandatory and is the foundation of the Database Creation
Engine design.
